# Contributing to Sloppi

Thank you for your interest in contributing to **Sloppi**! 

Sloppi is an agentic design intelligence skill designed to prevent coding agents from producing generic, repetitive, low-intent frontend interfaces. We welcome contributions that improve design reasoning, enhance research reference routing, refine visual QA audits, or improve framework adaptation.

---

## 1. The Cardinal Contribution Rule

> **Important**: Adding a personal aesthetic preference is **NOT** the same thing as adding a Sloppi principle.

Sloppi is **anti-default, not anti-style**. We do not accept contributions that attempt to force a single visual aesthetic (e.g. *"all websites must use brutalist typography"* or *"all cards should be banned"*). 

Contributions must be grounded in **structural design reasoning**, **mathematical ratios**, **accessibility standards**, or **verifiable ergonomics**.

---

## 2. How to Propose Changes

We welcome contributions in the following areas:

1. **Methodology Improvements**: Refining diagnostic questions, improving root-cause tracing, or strengthening the 7-pass implementation protocol.
2. **Reference Channels**: Suggesting high-quality, specialized design galleries for `references/source-registry.md`.
3. **Audit Signals & Rules**: Identifying new AI default patterns and defining their structural remediation in `audit/anti-slop-audit.md`.
4. **Workflows & Checklists**: Adding concise operational recipes for specific tech stacks (e.g. Astro, SvelteKit).

---

## 3. Pull Request Guidelines

When submitting a Pull Request, please ensure:

- [ ] **Traceable Rationale**: Explain *why* the proposed change improves design reasoning or agent execution.
- [ ] **No Stylistic Dogmatism**: Verify that the change does not restrict agents to a single aesthetic.
- [ ] **Dual-Directory Parity**: If modifying files in root modules (e.g. `audit/`, `content/`), ensure corresponding files in `sloppi/` are kept in sync.
- [ ] **Relative Links Only**: Use relative Markdown links; never hardcode local machine paths.
- [ ] **Self-Contained Documentation**: Every methodology file must be clear, actionable, and free of conversational artifacts.

---

## 4. Development & Testing

Before submitting your PR:
1. Run the **10 Diverse Project Evaluation Test** to verify that your change does not cause visual convergence across different archetypes (e.g. Developer Tool vs. Luxury vs. Fintech).
2. Review the **Pre-Ship Checklist** in `checklists/pre-ship.md`.
